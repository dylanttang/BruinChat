# Group DMs Plan (Issue #116)

**Goal:** People can start a group chat with classmates (up to 20 people), name it or leave it unnamed, add classmates, rename it and leave it. The server enforces who can be added.

**Approach:** Build for the final product, not the quickest version. Every chat gets an explicit kind instead of the app guessing from `isGroup` and `course`. Membership changes show as notices in the chat ("Rex added Ana"). Existing class chats, DMs, the BChat Team chat and the App Store review demo chat must keep working, including on app versions already installed on phones.

**Status:** Planning. Plan reviewed by GPT-6.2 Sol (2026-11-24) and revised. Server first, while Eusern builds the classmate picker (#82). App screens wait on the design team.

**Branch:** `rex/group-chats`. Server and app may ship as separate PRs; the server PR must be safe with today's app.

## Decisions (Rex, 2026-11-24)

- **Chat kind:** every chat gets `kind`: `class`, `direct`, `group` or `team`. Backfilled once for existing chats. Server code reads `kind`, never infers from `isGroup`/`course`. #117 (Classes and DMs on one screen) relies on this.
- **Who can be added:** only people who share a class chat with the person adding them right now, with no block in either direction between those two, and not banned or deleted. Checked on the server on create and on add; the app's list is never trusted.
- **Shared-class check:** one server helper, also used by Eusern's classmates endpoint (#82). Rex writes it first and tells Eusern.
- **Blocks inside a group:** members with a block between them both stay. Hiding follows each viewer's own block list, exactly as in class chats today: you don't see messages, previews, typing or pushes from people you blocked; someone who blocked you stops seeing you. Adding is refused only when the adder and the person being added have a block between them. Every refusal (not a classmate, blocked, banned, deleted) returns the same generic reason, so the API confirms neither blocks nor class enrollment.
- **History:** anyone added sees the group's earlier messages (including rejoining after leaving), like most group chats. Message history access stays "current member sees everything".
- **After the quarter:** members stay in the group when they no longer share a class (dropping a class only removes you from that class chat). The class rule applies only at the moment someone is added.
- **Same people twice:** picking one person reopens the existing DM (`POST /direct`). Picking several always creates a new group.
- **Name:** optional, up to 50 characters. With no name, the title is built from members' names. Anyone in the group can rename it or clear the name.
- **Notices:** "X created the group", "X added Y and Z", "X renamed the group to …", "X removed the group name", "X left". Shown as small centered text, not a bubble. They don't make a chat unread, don't send pushes, and can't be edited, deleted, reacted to, replied to or threaded.
- **Spam limits:** at most 20 members per group (including the creator), at most 10 new groups per person per rolling 24 hours (deleting a group does not give the slot back), and rate limits on adds and renames. Getting added sends a push. Muted or banned users can't create, add or rename.
- **Permissions:** anyone in the group can add, rename and leave. Nobody can remove someone else (no admin roles yet). `createdBy` is kept so admin roles can be added later without a migration.
- **Leaving and archiving:** group DMs get "Leave group". The last person leaving (or deleting their account) deletes the group, its messages and their media. Group DMs can also be archived like DMs (hidden for you, still a member), and the Archived screen (sample data today) becomes real so you can bring them back.
- **Notices and moderation:** notices can't be reported. Abusive group names are out of scope for now (see Not in scope).

## Done when

- [ ] Create a group of three or more; everyone sees it in their list and gets messages live and as pushes
- [ ] Add people, rename (and clear the name), and leave, each with a notice in the chat
- [ ] Can't add someone you don't share a class with, someone with a block either way, or a banned or deleted account, even by calling the API directly (tests)
- [ ] Member cap and daily group limit hold, including two adds at the same moment (tests)
- [ ] Existing class chats, DMs, the team chat and the review demo chat still list, open, send, notify, archive and leave as before, on both the new app and the currently released app
- [ ] `npm test` (server), `npx tsc --noEmit` (client) and `npm run test:security` pass

## Compatibility with the released app

The app already on phones reads `isGroup`, `course` and `name`, and asks for `?kind=group` (class list) and `?kind=direct` (DM list). The server PR must not break it:

- Group DMs keep `isGroup: true`, so old apps treat them like any group chat rather than as a broken 1-on-1 DM.
- Old apps' `?kind=direct` keeps returning only 1-on-1 DMs; `?kind=group` keeps returning everything else (classes, team, review demo, and now group DMs). Old apps will show group DMs in the class list. Acceptable until they update.
- Every chat response includes a usable `name`. For an unnamed group the server fills `name` with the generated title for the viewer, and sends `customName` (string or null) so new apps know whether a real name was set.
- Notices carry plain `text` ("Rex added Ana") and a real `senderId` (the person who did it), populated and sent through `serializeMessage` like any message (the released app reads `senderId._id` on `newMessage`), so old apps show them as an ordinary message from that person instead of crashing.
- New apps ask for lists with a new parameter (see step S3) so old values keep their meaning.

## Steps

Status: `[ ]` todo, `[~]` in progress, `[x]` done. Each server step lands with its tests so work can stop safely after any step.

### S1. Chat kind (the risky step; do and check this alone first)

Rolled out in three phases so no deploy order can break anything:

**Phase 1 (deploy): write `kind`, read with a fallback.**
- [ ] `models/Chat.js`: add `kind: { type: String, enum: ['class', 'direct', 'group', 'team'] }`, **not required yet**. Add an index on `{ members: 1, kind: 1, lastMessageAt: -1, _id: -1 }`. Keep `isGroup` and `course` (old apps read them).
- [ ] Set `kind` at every place chats are created: class enrollment (`server/routes/users.js` `PUT /me/courses`, `$setOnInsert`), `POST /api/chats/direct`, review demo chat (`server/utils/reviewLogin.js`), `scripts/seed.js`.
- [ ] One helper `chatKind(chat)`: stored `kind`, else `course` set → `class`, `isGroup: false` → `direct`, else `team`. All in-memory branching uses it: `directRecipientAvailable`, push titles (`isDirect`, `isClassChat`), leave route, mentions.
- [ ] Database queries keep their legacy predicates in this phase (list filter and its cursor lookup, DM lookup by `isGroup: false` + 2 members for pre-`directKey` DMs), so kindless rows are never filtered out. `archiveTerm.js` stays course-based.

**Phase 2 (run after phase 1 is live everywhere): backfill.**
- [ ] `scripts/backfillChatKind.js`, idempotent, dry-run by default, `--apply` to write, same mapping as `chatKind`. Prints counts per kind. Finish by verifying zero chats without `kind`. Staging first, then production.

**Phase 3 (deploy after the backfill verifies zero missing): require it.**
- [ ] Make `kind` required. Queries may now filter by `kind` (S3 `section=` lists). Keep the `chatKind` fallback for one more release, then remove it.
- [ ] Group DMs (S4 onward) ship in or after phase 3, so every query that sees a group already has `kind`.

**Tests and checks**
- [ ] Each creation path sets the right kind; backfill maps each old shape correctly; old `?kind=group` / `?kind=direct` results and cursors unchanged; a legacy kindless chat can still be left and saved.
- [ ] Manual check on the simulator: class chat, DM, team chat and review demo chat list, open, send, notify, archive and leave as before.

### S2. Who can be added (shared helper)

- [ ] `server/utils/classmates.js`: `findAddableClassmates(adder, candidateIds)` returns which candidates pass and why the rest fail (`not_classmate`, `unavailable`). One query each: class chats the adder is in (`kind: 'class', members: adder`), then users in `candidateIds` who are members of any of those chats, not banned, not deleted, not in `adder.blockedUsers`, and whose `blockedUsers` doesn't contain the adder. The review account (`isReviewAccount`) is in no real class chats, so it can't add or be added.
- [ ] The same module exports the query Eusern's `GET /api/users/me/classmates` (#82) uses, so the picker and the server rule always agree.
- [ ] Externally every failure is the same `unavailable` reason (internal reasons are for logs and tests only), so the response reveals neither blocks nor enrollment.
- [ ] Known small race: a block, ban or class drop landing at the same instant as an add can let that add through. Acceptable; the block still hides messages, and the person can leave.
- [ ] Tests: stranger, classmate, blocked by adder, blocked the adder, banned, deleted, self, duplicate IDs, invalid IDs, someone sharing a class only via a class chat the adder left.

### S3. Listing chats

- [ ] `GET /api/chats` gains `section=classes` (`kind` in `class`, `team`) and `section=messages` (`kind` in `direct`, `group`). Old `kind=` values keep their current meaning. New apps use `section`.
- [ ] One viewer-aware formatter `formatChatForViewer(chat, viewerId)` used by every chat response (list, archived, single, archive toggle, create, add, rename): populated members, `kind`, `customName`, and `name` filled with the generated title when there's no custom name.
- [ ] Generated title for unnamed groups: first names of other members (excluding the viewer and deleted accounts), "Ana, Ben and Cam" up to three, then "Ana, Ben and 3 others". One helper, used by the formatter and per-recipient push titles.
- [ ] Schema: `name` stops being required for `kind: 'group'` (still required for other kinds via a conditional validator); stored absent when there's no custom name.
- [ ] Unread metadata: the list aggregation tracks two things per chat, the latest visible item (any message or notice, for the preview text and ordering) and the latest visible ordinary message (for `lastMessageSenderId`/`lastMessageCreatedAt`, which drive unread). A notice after an unread message no longer hides that message.
- [ ] Tests: sections return the right kinds; pagination cursors work within a section; generated titles.

### S4. Creating a group

- [ ] `POST /api/chats/group`, body `{ memberIds: string[], name?: string }`. Uses `requireAuth`, the posting block (`postingBlock`: muted or banned users can't create), and a new `groupCreateRateLimit`.
- [ ] Validation: `memberIds` is an array of 2 to 19 valid unique IDs, not including the caller (if exactly 1 ID, return 400 telling the app to use `/direct`). `name` is optional, trimmed, 1 to 50 characters after trim, run through the same text checks as messages (`validateText`); empty becomes no name.
- [ ] Daily limit: on the user, keep `groupCreations: [Date]`. Reserve a slot with one atomic update that pulls entries older than 24 hours and pushes now only if fewer than 10 remain (conditional update on the array size); refuse with 429 otherwise. Concurrent creates can't both pass, deleting groups doesn't refund, and it survives restarts. Reserve before creating; a failed create keeps the slot used (simple and conservative).
- [ ] All-or-nothing: if any member fails S2, return 400 with the failing IDs and reasons, create nothing.
- [ ] Create with `kind: 'group'`, `isGroup: true`, members = caller + others, `createdBy` caller, `name` (or none), `lastMessageAt` now. Then post the "created" notice (S7), then emit `chatAdded` to each member's `user:<id>` room and push (S8). Events go out only after the database writes succeed. If the notice write fails, the group still exists and the error is logged (a missing notice is harmless; no rollback).
- [ ] Tests: happy path, member-count bounds, duplicate and self IDs, any failing member blocks creation, muted user, daily limit, name validation, caller-supplied extra fields (`kind`, `createdBy`, `course`) ignored.

### S5. Adding people

- [ ] `POST /api/chats/:id/members`, body `{ memberIds: string[] }` (1 to 19). Caller must be a member, chat must be `kind: 'group'`. Same S2 check against the caller. Skip IDs already in the group.
- [ ] Member cap without races: one conditional update that adds only if the group still has room, e.g. filter `{ _id, kind: 'group', members: caller, ['members.' + (20 - toAdd.length)]: { $exists: false } }` with `$addToSet: { members: { $each: toAdd } }`, returning the document as it was before the update. If no document matched, reload: if the people are now already members (someone else added them), return success with nothing added; if still no room, 409 "This group is full"; if the caller left, 403.
- [ ] Compute the real delta from the pre-update document (only people who weren't already members). Use only that delta for clearing `archivedBy`, the "added" notice, `chatAdded`, and pushes, so overlapping adds never double-notify. Empty delta: no notice, no pushes. Emit `chatUpdated` to the chat room.
- [ ] `postingBlock` applies (muted or banned users can't add).
- [ ] Rate limit: new `groupMemberRateLimit` (e.g. 30 adds per hour per user).
- [ ] Tests: class/block/ban rules via direct API calls, non-member caller, class chat or DM target (refused), already-members skipped, cap of 20 including two concurrent adds, rate limit.

### S6. Renaming and leaving

- [ ] `PATCH /api/chats/:id`, body `{ name: string | null }`. `postingBlock` applies, new `groupRenameRateLimit` (e.g. 20 per hour). The write itself filters on `{ _id, kind: 'group', members: caller }` so someone who just left can't rename. Same name rules as S4; null or empty clears. No-op if unchanged (no notice). Notice "renamed to …" or "removed the group name". Emit `chatUpdated`.
- [ ] `DELETE /api/chats/:id/members/me`: allow `kind: 'group'` (and keep class/team behavior). Fix the empty-chat delete, which never runs today because it checks `!chat.isGroup` after DMs are turned away. For groups: remove the caller with an atomic `$pull`; if no members remain, run the shared cleanup.
- [ ] Shared `removeFromGroup(chatId, userId, { notice })` used by leave and account deletion: atomic `$pull`, "left" notice if others remain, `chatUpdated`, socket room leave. `cleanupEmptyGroup(chatId)` deletes the chat only if `members` is still empty (conditional delete), then its messages and media; safe to re-run. A message sent while the last person leaves can at worst leave orphan messages, which a re-run of cleanup (or a small sweep in `scripts/`) deletes.
- [ ] Leaving a class chat is unchanged (it's done through the courses list in the app).
- [ ] Tests: rename by non-member, rename of class chat refused, clear name, unchanged name, leave last member deletes chat and messages, leave with others posts notice, DMs still refused.

### S7. Notices

- [ ] `models/Message.js`: optional `system` subdocument `{ type: enum ['created', 'added', 'renamed', 'left'], targetIds: [ObjectId], name: String }`, `default: undefined` so ordinary messages never get it. `senderId` is the actor. `text` is the plain-language version for old apps and previews ("Rex added Ana and Ben").
- [ ] One helper `postNotice(chat, actor, type, details)` creates the message, updates `lastMessageAt`, then emits `newMessage` with the populated, serialized message.
- [ ] Notices never trigger pushes or mention handling.
- [ ] Refuse edit, delete, react, reply-to, starting a thread and reading a thread on notices (each existing route checks `message.system`, including thread GET). Search skips notices.
- [ ] Reports: refuse `targetType: 'message'` when the message is a notice. While there, require the reporter to be a member of the message's chat (missing today, `server/routes/reports.js` accepts any message ID). Admin removal can't target notices.
- [ ] Chat list: preview text may be a notice; unread uses the latest ordinary message (S3). Old apps may show a dot for a notice; acceptable.
- [ ] Account deletion (`DELETE /api/users/me`): exclude notices from the "blank my messages" update so group history stays readable (the actor shows as "Deleted user"). Replace the bulk membership pull for `kind: 'group'` chats with `removeFromGroup` (so empty groups get cleaned up and others see "left"); keep the bulk pull for other kinds. Disconnect the user's sockets (`io.in('user:<id>').disconnectSockets(true)`).
- [ ] Tests: each notice type, notice-proof edit/delete/react/reply routes, no pushes.

### S8. Notifications and live updates

- [ ] Push when added: title is the group's title, body "Rex added you". Same filters as message pushes (master switch, banned, deleted, blocked the adder). `classNotif` does not apply to groups.
- [ ] Message pushes in unnamed groups: the title is per recipient (generated titles exclude the viewer), so group recipients by title before sending. Named groups and class chats keep one batch.
- [ ] Socket events: `chatAdded` (to `user:<id>`, so the inbox can refresh), `chatUpdated` with the new name and members (to the chat room). Membership changes don't need room joins; clients join on open and the server checks membership.
- [ ] Tests: push filters for "added", payload has `chatId`.

## Not in scope

- Removing other members, admin roles, group photos, muting a single group, invite links, adding people who aren't classmates.
- Showing group DMs and classes on one screen (#117).
- Reporting a group name (reports cover messages and users today); revisit if group names get abused.
- Pre-existing, affects class chats too, track as separate issues: a reply preview can show the quoted text of someone you blocked (`populateMessage` in `server/routes/chats.js`); hiding is one-way (someone who blocked you still sees you, by design).
